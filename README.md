# Стенд для теста AI-автоматизации

Это маленький стенд, на котором проверяется одна идея: **модель извлекает факты из чата, а решения принимают обычные правила**.

Если коротко:

```text
CRM + чат
   → фильтр шума + context rescue
   → LLM извлекает claim
   → валидатор цитаты и времени
   → resolver исправлений
   → правила из rules.json выносят вердикт
   → сводка + метрики + лог
```

Модель **не** выбирает приоритет и **не** закрывает кейсы. Она отвечает только на вопрос: «что именно утверждается в этом сообщении?». Поэтому даже если модель ничего не нашла, вердикт всё равно считается из CRM. Это главное защитное свойство всей конструкции.

---

## Первый запуск

Первый запуск — это четыре шага.

1. Поставьте Ollama и скачайте модель.
2. Укажите адрес API и имя модели в переменных окружения.
3. Сначала прогоните `--show-prompts`, `--fixture` и `--dry-run`. Они ничего не стоят и сразу показывают, исправна ли разметка.
4. Запустите обычный прогон. Если 7B-модель прогревается дольше двух минут, добавьте `--timeout 300`.

Что должны увидеть на третьем шаге:

- `--fixture` → `rule_match 4/4` и `claim_precision/recall 1.0`;
- `--dry-run` → `p1_recall 1.0` и `rule_match 3/4`. Без чата не сработает только правило `DELAY_CONFIRMED`, которому нужен claim из сообщения.

После обычного запуска полный лог появится в `runs/runs.jsonl`.

```bash
ollama pull llama3.2

export LLM_BASE_URL=http://localhost:11434/v1
export LLM_MODEL=llama3.2

python3 test_harness.py --show-prompts
python3 test_harness.py --fixture
python3 test_harness.py --dry-run
python3 test_harness.py
```

## Как подключить модель (любую LLM)

Код менять не нужно. `test_harness.py` умеет разговаривать с любым **OpenAI-совместимым** эндпоинтом `/v1/chat/completions`. Он сам соберёт путь: если в `LLM_BASE_URL` уже есть `/v1`, воспользуется им, иначе допишет.

### Что передаётся в модель

- `model` — из `LLM_MODEL`;
- `messages` — системный промпт из `AGENTS.md` и один пользовательский промпт с подстановками;
- `temperature: 0`;
- заголовок `Authorization: Bearer <LLM_API_KEY>`.

Ответ должен быть текстом с JSON. Если модель обернула JSON в markdown-блок с пометкой `json`, стенд это переживёт. Но лучше, чтобы модель сразу возвращала только JSON — это прописано в `AGENTS.md`.

### Переменные окружения

| Переменная | По умолчанию | Что это |
|---|---|---|
| `LLM_BASE_URL` | `http://localhost:11434/v1` | Адрес OpenAI-совместимого API |
| `LLM_API_KEY` | `ollama` | Bearer-токен. Для локальных моделей можно оставить как есть |
| `LLM_MODEL` | `llama3.2` | Имя модели так, как его знает сервер |
| `LLM_TIMEOUT` | `120` | Таймаут одного запроса. Для холодного старта больших моделей — `300` |
| `PROMPT_VERSION` | `extract_v3` | Метка промпта в логе; помогает сравнивать прогоны |

### Готовые варианты

**Ollama — самый простой локальный вариант**

```bash
ollama pull llama3.2
# или: ollama pull qwen2.5:7b (Я тестировал на qwen2.5:7b)

export LLM_BASE_URL=http://localhost:11434/v1
export LLM_API_KEY=ollama
export LLM_MODEL=llama3.2

python3 test_harness.py --timeout 300
```

**llama.cpp server — если важна скорость на своём железе**

```bash
# сервер должен быть поднят с OpenAI-совместимым роутом /v1
export LLM_BASE_URL=http://localhost:8080/v1
export LLM_API_KEY=local
export LLM_MODEL=model

python3 test_harness.py --timeout 300
```

**OpenRouter**

```bash
export LLM_BASE_URL=https://openrouter.ai/api/v1
export LLM_API_KEY=sk-or-ваш-ключ
export LLM_MODEL=meta-llama/llama-3.3-70b-instruct

python3 test_harness.py
```

**OpenAI**

```bash
export LLM_BASE_URL=https://api.openai.com/v1
export LLM_API_KEY=sk-ваш-ключ
export LLM_MODEL=gpt-4o-mini

python3 test_harness.py
```

**vLLM или свой гейтвей**

```bash
export LLM_BASE_URL=http://localhost:8000/v1
export LLM_API_KEY=dummy
export LLM_MODEL=имя-из-конфига-сервера

python3 test_harness.py
```

Команды для llama.cpp, OpenRouter, OpenAI и vLLM приведены как готовые примеры, но сами прогоны на них не делались — проверены только локальные Ollama-модели. См. раздел «Нужно проверить».

Отдельный API-гейтвей для модели **не обязателен**: для четырёх кейсов и одной модели достаточно прямого подключения. Он становится полезным позже — когда нужны версионирование промптов, кэш, лимиты, retry, redaction персональных данных и переключение провайдеров без правки стенда. Если у провайдера нет OpenAI-совместимого API, гейтвей или маленький адаптер всё равно понадобится.

### Как понять, что подключение работает

```bash
python3 test_harness.py --show-prompts    # что именно видит модель
python3 test_harness.py --fixture        # стенд без модели — эталон
python3 test_harness.py --dry-run        # правила без чата
python3 test_harness.py --timeout 300    # уже с моделью
```

| Симптом | Что проверить |
|---|---|
| `404 Not Found` | В `LLM_BASE_URL` не хватает `/v1`, либо сервер поднят на другом порту |
| `401 / 403` | Неверный или отсутствующий `LLM_API_KEY` |
| `model not found` | Имя из `LLM_MODEL` не совпадает с тем, что отдаёт `ollama list` или сервер |
| Долгий первый запрос | Холодный старт: `--timeout 300` или `LLM_TIMEOUT=300` |
| Модель отвечает markdown вместо JSON | Посмотреть `raw` в логе; в `AGENTS.md` уже сказано «только JSON» |
| Цитата не находится в тексте | Открыть `--explain CASE_ID`: там видно ответ модели и результат валидатора |
| `p1_recall < 1.0` | Сначала `--fixture`. Если там всё хорошо — проблема в извлечении или фильтре; сравнить с `--no-coarse-filter` |

### Четыре случая

| Кейс | Что в CRM | Приоритет | Почему |
|---|---|---|---|
| `С-17` | Ожидаются документы | `P2` | Нужно проверить документы у руководителя и загрузить в CRM |
| `С-24` | Подтверждение нужно от руководителя, его нет | `P1` | Просьба сотрудника «в курсе» не считается подтверждением |
| `П-08` | Доставка до 10:00, статус «В пути», срок нарушен | `P1` | `SLA_BREACH`; начинать стоит именно с него |
| `П-09` | Всё принято, открытых пунктов нет | `—` | Закрыть без действий |

## Инструкция для модели

Откройте `AGENTS.md`. Она разделена на две секции:

- `## SYSTEM` — роль, запрет выполнять инструкции из чата, схема выходного JSON, список типов `claim_type`;
- `## USER` — примеры и подстановки `$case_id`, `$case_type`, `$crm`, `$history`, `$msg_id`, `$author`, `$author_role`, `$ts`, `$text`.

`SUPERSEDES` и `$history` нужны для исправлений: модель видит последние три реплики того же автора и может отметить, какую именно прежнюю задержку она отменяет. Финальный выбор всё равно делает resolver — побеждает последнее по времени ETA-утверждение автора, даже если модель неправильно указала `supersedes`.

Промпт можно править без правки кода. Если изменили `AGENTS.md`, поднимите `PROMPT_VERSION`, чтобы в логе было видно, какой версией получен результат.

## Правила как данные

Правила раньше были `lambda`-функциями внутри Python. Теперь они лежат в `rules.json`:

```json
{
  "severity_order": { "—": 0, "P3": 1, "P2": 2, "P1": 3 },
  "rules": [
    {
      "id": "SLA_BREACH",
      "severity": "P1",
      "action": "Зафиксировать новое ETA, уведомить точку, эскалация логистике",
      "when": {
        "all": [
          { "field": "type", "op": "eq", "value": "delivery" },
          { "field": "crm.deadline", "op": "lte_field", "value": "now" },
          { "field": "crm.status", "op": "ne", "value": "Принято" }
        ]
      }
    }
  ]
}
```

Операторы: `all/any/not`, `eq/ne/in`, `truthy/falsy`, `some` по списку claims и `lte_field` для сравнения дат. Неизвестный оператор вызывает ошибку — правило не может тихо не сработать.

```bash
python3 test_harness.py --rules rules_new.json --fixture
```

Если сценарий ни под одно правило не попал, вердикт будет `FALLBACK` / ручная сверка, а не «закрыть».

### Разбор одного кейса

```bash
python3 test_harness.py --fixture --explain П-08
```

Команда печатает CRM, все сообщения, фильтр и context rescue, точные промпты, ответ модели, проверки цитаты и ETA, отброшенные resolver'ом claim'ы и **каждое правило с пометками `OK` / `NO` у каждого условия**. Формат основного JSONL при этом не меняется.

## Что смотреть в выводе

1. **Сводка** — четыре строки с приоритетом и действием плюс строка «Начать с».
2. **Метрики вердикта**

| Метрика | Цель |
|---|---|
| `p1_recall` | `1.0` — все настоящие P1 найдены |
| `false_close` | `0` — ни одного закрытия там, где нужно действие |
| `unknown_rate` | `< 0.1` — не слишком много `FALLBACK` |
| `rule_match` | Совпадение набора правил с ожидаемым |

3. **Метрики извлечения**

| Метрика | Смысл |
|---|---|
| `claim_precision / recall` | Совпали ли тип, автор, ETA и `supersedes` |
| `quote_valid` | Цитата реально есть в сообщении; цель `1.0` |
| `vague_eta` | Сколько раз поймано размытое время («к часу», «после обеда») |
| `context_rescued` | Сколько сообщений прошло по недавней реплике того же автора |
| `noise_rejected` | Сколько шума отсеялось до модели |

4. `runs/runs.jsonl` — полный лог: вердикт, правила, claims, ответы модели, ошибки.

## Проверено на практике

Ниже — только то, что реально прогонялось.

### `llama3.2:3b`, Ollama

| Прогон | Вердикт | Извлечение |
|---|---|---|
| `cases.json` | `p1_recall 1.0`, `rule_match 4/4` | `precision/recall 1.0` |
| `cases_paraphrase.json` | `p1_recall 1.0`, `rule_match 3/4` | `0/4`; реплику П-08 съел keyword-фильтр |
| paraphrase + `--no-coarse-filter` | `p1_recall 1.0`, `rule_match 4/4` | `1/2`, один claim в `review` |

Вывод: 3B-модель годится для проверки конвейера и защитных свойств, но слабо справляется с семантикой. Вердикт при этом оставался правильным за счёт CRM.

### `qwen2.5:7b`, Ollama

| Прогон | Вердикт | Извлечение |
|---|---|---|
| `cases_paraphrase.json`, фильтр включён | `rule_match 3/4` | `precision 1.0`, `recall 0.75` |
| `--no-coarse-filter`, ранняя версия промпта | `rule_match 4/4` | `eta` вместо `null` было «ближе к часу дня» |
| `--no-coarse-filter`, `extract_v2_qwen25_7b_nofilter` | `rule_match 4/4` | `precision/recall 1.0`, `quote_valid 4/4`, `review_queue 0` |
| после рефакторинга, `--timeout 300` | `rule_match 4/4` | `precision/recall 1.0`, `quote_valid 4/4`; галлюцинацию `13:00` валидатор сбросил в `null` |

Вывод: 7B-модель уверенно справляется с переформулировками. Главный риск был не в модели, а в грубом фильтре: фраза «Немного застрял на трассе…» не содержала ключевых слов и терялась до вызова LLM.

### Отдельные механики

| Механика | Проверка | Результат |
|---|---|---|
| Исправление ETA | `cases_correction.json`, с фильтром и без | `rule_match 2/2`, `precision/recall 1.0`, `quote_valid 4/4` |
| Размытое время | `cases_paraphrase.json` | `rule_match 4/4`, `vague_eta 1`, `eta_hint = «ближе к часу дня»` |
| Context rescue | `cases_rescue.json`, qwen | `rule_match 1/1`, `context_rescued 1`, `review_queue 0` |
| Вынесенные правила | `--rules` с изменённым severity | Приоритет П-08 изменился с `P1` на `P2` — значит правила реально управляются файлом |
| Старый и новый лог | Сравнение набора ключей JSONL | Полностью совпали |

## Нужно проверить

Это честный список того, чего в стенде **нет** или что не прогонялось:

- Метрики стоимости и задержек: `requests`, `latency_ms`, `prompt_chars` пока не считаются.
- Локальный классификатор шума `TF-IDF + LogisticRegression`: схема есть, но учить не на чем — нет реальных сообщений.
- Файнтюн или дистилляция модели: не делались. Размытое время сейчас ловится детерминированным regex, а не весами модели.
- Гарантии детерминизма: `temperature: 0` не делает ответы полностью предсказуемыми, поэтому валидаторы обязательны.

## Полезные команды

```bash
# Посмотреть, что именно увидит модель
python3 test_harness.py --show-prompts

# Проверить стенд без модели
python3 test_harness.py --fixture

# Проверить защиту CRM-only: правила без чата
python3 test_harness.py --dry-run

# Отключить грубый фильтр — эталон корректности извлечения
python3 test_harness.py --no-coarse-filter

# Разобрать конкретный кейс
python3 test_harness.py --explain П-08

# Подменить правила
python3 test_harness.py --rules rules_new.json --fixture

# Добавить свой кейс: допишите объект в cases.json с полем "expected"
python3 test_harness.py --cases cases.json --out runs/experiment_1.jsonl
```

Свой кейс можно проверить на любой модели: достаточно поменять три переменные окружения и, при необходимости, передать `--timeout`.
